# 2025-12-29 - Chat Input Box UX Improvements

## Issues Identified

### Issue 1: Command text doesn't clear after selection
**Problem**: When user selects `/code` from the command menu, the input shows "/code " instead of clearing. This leaves the command syntax visible in the input box.

**Current behavior**:
- Type "/" → menu appears
- Select "/code" → input shows "/code "
- User must manually delete or type after it

**Expected behavior**:
- Type "/" → menu appears
- Select "/code" → input clears, chip appears
- User types message in clean input

**Root cause**: `handleCommandSelect()` in ChatInput.tsx:77 sets input to `command.command + " "` which keeps the slash command visible.

### Issue 2: Command chip positioned on border instead of inline
**Problem**: The active command indicator (blue chip) appears on the border of the input box using absolute positioning (`-top-3`), rather than appearing inline within the input area like Slack/Discord.

**Current implementation** (ChatInput.tsx:125-129):
- Chip absolutely positioned above the border
- Shows "/code" (with slash)
- No way to dismiss except sending message

**Desired implementation**:
- Chip appears inside the input box, before the text
- Shows "code" (without slash)
- Includes X button to dismiss
- Text input has left padding to accommodate chip

## Solution Design

### Approach: Separate command state from input text

Instead of encoding the command in the input string ("/code message"), track the selected command as separate state and keep the input clean.

**Key changes**:
1. Add `selectedCommand` state to track active command
2. Clear input completely when command is selected
3. Position chip inside input area with overlay
4. Adjust textarea padding when chip is shown
5. Allow dismissing command with Escape or X button
6. Display command name without "/" prefix

### Implementation Files
- **Primary**: `frontend/app/components/ChatInput.tsx`
- **No changes needed**: `frontend/hooks/useSlashCommands.ts` (hook logic remains the same)

### UX Flow After Fix
1. User types "/" → menu appears with command options
2. User selects "/code" → menu closes, input clears, blue "code" chip appears inside input
3. User types message → text appears after chip with proper spacing
4. User can click X or press Escape to remove chip
5. User can type "/" again to select different command
6. User presses Enter → message sent with `agent="code"`, input and chip cleared

## Design Rationale

The chip-based approach is superior to keeping command syntax in the input:

**Benefits**:
- Visual separation: command is metadata, message is content
- Cleaner UX: user focuses on writing message, not syntax
- Familiar pattern: similar to Slack mentions, Discord commands
- Space efficient: compact chip vs. text taking up input space
- Discoverability: visual indicator is more intuitive than text prefix

**Trade-offs**:
- Slightly more state management (acceptable complexity)
- Command syntax hidden from user (but they don't need to see it)
- Future extension to command arguments would need different UX (not currently needed)

# Vitest CJS Deprecation Warning Fix

## Problem

When running `vitest`, the following warning appears:

```
The CJS build of Vite's Node API is deprecated. See https://vite.dev/guide/troubleshooting.html#vite-cjs-node-api-deprecated for more details.
```

## Cause

Vitest (which uses Vite internally) is being loaded via CommonJS (`require()`) instead of ESM (`import`). This happens when the project's `package.json` doesn't signal to Node.js that it should use ESM.

## Solution

Add `"type": "module"` to `frontend/package.json`:

```json
{
  "name": "frontend",
  "version": "0.1.0",
  "private": true,
  "type": "module",  // <-- Add this line
  "scripts": {
    ...
  }
}
```

## Why This Works

- `"type": "module"` tells Node.js to treat `.js` files as ES modules by default
- This allows Vitest/Vite to load via ESM instead of the deprecated CJS API
- The warning disappears because Vite now uses its ESM build

## Alternative Solutions

If adding `"type": "module"` causes issues with other parts of your project:

1. **Rename config files to `.mjs`**: e.g., `vitest.config.mjs`, `vite.config.mjs`
2. **Use `.cjs` extension** for files that must remain CommonJS

# Slash Command Suggestion Buttons Fix

## Problem
Clicking slash command suggestion buttons on the welcome screen only focuses the input but doesn't select the command or show the chip.

## Root Cause
In `ChatInterface.tsx`, the button onClick handler only calls `chatInputRef.current?.focus()` without selecting the command.

## Solution
1. Extend `ChatInputRef` interface to include `selectCommand` method
2. Implement `selectCommand` in `useImperativeHandle` to set the selected command state
3. Update `ChatInterface.tsx` to call `selectCommand` when clicking suggestion buttons

## Files Modified

# Search API Comparison for Future `/search` Enhancement

When implementing an enhanced `/search` slash command (beyond Gemini's built-in `googleSearch` grounding), here's a comparison of available options:

| Feature | Tavily | Brave Search | SerpAPI/Google |
|---------|--------|--------------|----------------|
| **Purpose-built for LLM** | Yes | No | No |
| **Free tier** | 1000 req/mo | 2000 req/mo | 100 req/mo |
| **Pricing** | $0.01/req | $0.009/req | $0.05/req |
| **Response format** | LLM-optimized (summarized) | Raw results | Raw results |
| **Setup complexity** | Simple | Simple | Medium |
| **Result quality** | Good | Good | Best (Google) |

## Recommendation

**Tavily** for `/search` slash command enhancement:
- Designed specifically for AI/LLM applications
- Returns clean, summarized content ready for LLM consumption
- Simple API with good documentation
- Reasonable pricing for production use

## Use Case Differentiation

| Scenario | Tool |
|----------|------|
| Default chat (weather, news, facts) | Gemini's built-in `googleSearch` grounding |
| `/search` command (explicit, thorough) | Tavily API with multiple sources, citations |

## Implementation Notes

For `/search` slash command:
1. User explicitly requests search → call Tavily API
2. Return structured results with sources
3. Format citations for display
4. Consider caching for repeated queries

# Default Agent Implementation with Gemini

## Overview

Replaced the mock default agent with a real Gemini integration, including:
- Streaming responses
- Built-in `googleSearch` grounding (enabled by default)
- Built-in `codeExecution` tool (enabled by default)
- Real-time status bubbles showing tool usage
- System prompt with current date and time

## Design Philosophy

| Mode | Behavior |
|------|----------|
| **Default Agent** | Capable generalist - uses search/code tools when naturally needed |
| **Slash Commands** | Enhanced/specialized modes with deeper focus (future) |

The default agent should handle common queries like "What's the weather?" or "Calculate 15% tip" without requiring explicit slash commands.
