# Dev Notes: 2026-01-06

## Fix: Rich Travel UI Rendering Bugs

### Issues Identified

The Rich Travel UI enhancement (v0.9.0) shipped with several critical bugs:

1. **All components in single bubble** - Highlights, Itinerary, Budget rendered together instead of separate messages
2. **Images showed fallback emoji** - Unsplash Source API failing/rate-limited
3. **Results waited for all agents** - No progressive loading, long wait time
4. **Itinerary missing** - JSON parsing failures caused itinerary not to render
5. **Cards too small** - 208px width was unusable, user wanted one attraction at a time

### Root Cause Analysis

See detailed issue: `.issues/rich-travel-ui-rendering-bugs.md`

**Key problems:**
- `useChat.ts` stored all three travel data fields on the same Message object via `updateLastMessage()`
- Unsplash Source API (deprecated) rate-limited without API key
- `DestinationHighlights.tsx` had fixed 208px cards with horizontal scroll
- JSON parsing failures silently fell back to text output

### Fixes Implemented

#### 1. Real Image URLs from LLM

**Problem**: Using placeholder API that failed.

**Solution**: Modified backend prompt to have LLM return actual Wikipedia Commons URLs.

```python
# backend/app/agents/travel_agent.py
research_task = Task(
    description=f"""...
    "attractions": [
        {{"name": "...", "description": "...", "imageUrl": "https://upload.wikimedia.org/wikipedia/commons/..."}}
    ]

    For imageUrl, you MUST provide actual working image URLs from:
    - Wikipedia Commons (https://upload.wikimedia.org/wikipedia/commons/...)
    ..."""
)
```

**Files changed:**
- `backend/app/agents/travel_agent.py` - Updated prompt
- `frontend/lib/types.ts` - Changed `imageQuery` to `imageUrl`
- `frontend/app/components/travel/DestinationHighlights.tsx` - Use `imageUrl` directly

#### 2. Full-Width Single-Slide Carousel

**Problem**: Cards were 208px wide, hard to see content.

**Solution**: Redesigned as single-slide carousel with one attraction at a time.

```tsx
// DestinationHighlights.tsx
const [currentIndex, setCurrentIndex] = useState(0);
const attraction = data.attractions[currentIndex];

return (
  <div className="relative aspect-video w-full">
    <img src={attraction.imageUrl} className="w-full h-full object-cover" />
    {/* Navigation arrows, dot indicators, slide counter */}
  </div>
);
```

**Features:**
- Full-width image (`aspect-video`)
- Previous/Next navigation buttons
- Dot indicators for each slide
- Slide counter (1/5, 2/5, etc.)

#### 3. Separate Messages for Each Section

**Problem**: All 3 components in one message bubble.

**Solution**: Each travel event creates a new assistant message.

```typescript
// useChat.ts - Before
case "travel_highlights":
  updateLastMessage({ travelHighlights: event.data });

// useChat.ts - After
case "travel_highlights":
  addMessage({
    id: generateId(),
    role: "assistant",
    content: "",
    timestamp: new Date(),
    agent: responseAgent,
    travelHighlights: event.data,
  });
```

**MessageBubble.tsx** now detects travel-only messages:
```tsx
if (message.travelHighlights && !message.content) {
  return (
    <div className="flex items-start gap-3">
      <MayaAvatar state="idling" size={56} />
      <DestinationHighlights data={message.travelHighlights!} />
    </div>
  );
}
```

#### 4. Better JSON Parsing & Logging

**Problem**: Itinerary missing due to silent JSON parsing failures.

**Solution**: Added task name to logging for debugging.

```python
def _parse_agent_json(self, raw_output: str, task_name: str = "unknown") -> dict | None:
    logger.info(f"Raw output from {task_name} (first 500 chars): {raw_output[:500]}")
    # ... parsing logic ...
    if not parsed:
        logger.error(f"Failed to parse JSON for {task_name}. Full output: {raw_output}")
```

## Consultation: Agent Architecture & Tool Design

### Current State Assessment

The travel agent currently uses a **linear/waterfall** approach:

```
User Input → Research Agent → Itinerary Agent → Budget Agent → Response
          (sequential, no tools, no inter-agent communication)
```

**Observations:**
- `Process.sequential` runs agents one after another
- No tools assigned to agents (they use pure LLM reasoning)
- Output is collected and streamed via SSE events
- Works fine but doesn't leverage CrewAI's full capabilities

### Vision: Autonomous Agents with UI Tools

**Concept:** Instead of "one agent = one task = one JSON blob," agents could:
1. Use tools to emit UI components progressively
2. Call each other or share context dynamically
3. Make autonomous decisions about what to show

**Example tool-based approach:**
```python
from crewai.tools import tool

@tool
def emit_attraction_card(name: str, description: str, image_url: str) -> str:
    """Emit a single attraction card to the UI."""
    # Push SSE event for one card
    return f"Displayed {name} card"

@tool
def emit_day_itinerary(day: int, activities: list) -> str:
    """Emit one day's itinerary to the UI."""
    return f"Displayed Day {day}"
```

This would enable:
- **Progressive UI**: Cards appear as agent discovers them
- **Real collaboration**: Research agent could call Budget agent mid-task
- **Richer interaction**: Agents respond to user mid-stream

### Trade-offs Analysis

| Approach | Pros | Cons |
|----------|------|------|
| **Current (Linear)** | Simple, predictable, easy to debug | No progressive feedback, all-or-nothing |
| **Tool-based Emission** | Progressive UI, more interactive feel | More complexity, harder to test |
| **Full Collaboration** | Agents can help each other, richer results | Much more complex, latency concerns |

### Key Concerns

1. **Latency**: More tool calls = more round trips = slower perceived response
2. **Reliability**: Each tool call is a potential failure point
3. **Debugging**: Harder to trace what went wrong in multi-agent dance
4. **Value vs Complexity**: Does richer interaction justify the added complexity?

### Staged Approach Recommendation

If pursuing this direction:

**Stage 1: Add Tools (Low Risk)**
- Create `@tool` decorated functions for common operations
- Test that agents can use them correctly
- Keep fallback to current approach

**Stage 2: Progressive UI Emission**
- Let agents emit UI components via tools
- User sees cards appear one-by-one
- Still sequential process, just more granular output

**Stage 3: True Collaboration**
- Switch to `Process.hierarchical` with manager agent
- Enable agents to call each other
- Most complex, only if Stages 1-2 show clear value

### Honest Opinion

The current implementation is **functional and appropriate** for a demo. The linear flow:
- Is predictable and debuggable
- Delivers complete results reliably
- Matches user expectations (ask → get answer)

The vision for autonomous, tool-using, collaborating agents is **interesting but may be over-engineering** for the current use case. It would make sense if:
- Users were doing complex multi-step planning
- Real-time responsiveness was critical
- The app needed to compete with sophisticated travel AI products

For now: **Document the vision, revisit if users request more interactivity.**

## Implementation: Stage 1 - Adding Tools to CrewAI Agents

### Motivation

Following the architecture consultation, implementing Stage 1 of the staged approach:
- Add tools to agents for operations that benefit from external data
- Keep existing flow intact (low risk)
- Test tool usage before proceeding to Stage 2 (progressive UI emission)

### Tools Implemented

|------|---------|-------|
| `lookup_wikipedia_image` | Find verified image URLs from Wikipedia API | Travel Researcher |

| `get_local_currency` | Look up country's currency code and name | Budget Analyst |

### Tool Details

#### 1. Image Lookup Tool (`image_lookup.py`)

Uses Wikipedia API to find verified image URLs for landmarks:

```python
@tool
def lookup_wikipedia_image(landmark_name: str, location: str = "") -> str:
    """Find a Wikipedia Commons image URL for a landmark."""
    # 1. Search Wikipedia for article
    # 2. Get page's main image via pageimages prop
    # Returns: "Image URL for {name}: https://upload.wikimedia.org/..."
```

**Key implementation details:**
- Requires User-Agent header (Wikipedia API policy)
- 10 second timeout to avoid blocking
- Graceful fallback: returns "No image found" on error

#### 2. Currency Tools (`currency.py`)

```python
@tool
def convert_currency(amount: float, from_currency: str, to_currency: str) -> str:
    """Convert amount between currencies."""
    # Uses exchangerate-api.com for live rates
    # Falls back to hardcoded rates if API fails

@tool
def get_local_currency(country: str) -> str:
    """Get the local currency for a country."""
    # Returns: "The local currency in Japan is JPY (Japanese Yen)"
```

**Key implementation details:**
- Live rates from free API (exchangerate-api.com)
- Fallback rates for 17 common currencies
- Country → currency mapping for 26 countries

### Agent Modifications

Modified `travel_agent.py` to attach tools:

```python
from .tools import convert_currency, get_local_currency, lookup_wikipedia_image

# Research Agent - has image lookup tool
researcher = Agent(
    role="Travel Researcher",
    backstory="""...Use the lookup_wikipedia_image tool to find real,
    working image URLs for each attraction.""",
    tools=[lookup_wikipedia_image],
    ...
)

# Budget Agent - has currency tools
budget_analyst = Agent(
    role="Budget Analyst",
    backstory="""...Use get_local_currency to find the destination's currency.
    Use convert_currency for accurate currency conversions.""",
    tools=[convert_currency, get_local_currency],
    ...
)
```

### Design Decisions

1. **No web search tool initially** - Can add later if needed for real-time travel info
2. **Planner has no tools** - LLM reasoning sufficient for itinerary creation
3. **All tools return strings** - Never raise exceptions, graceful fallbacks
4. **Short timeouts** - 5-10 seconds to avoid blocking crew execution
5. **User-Agent for Wikipedia** - Required by their API policy
