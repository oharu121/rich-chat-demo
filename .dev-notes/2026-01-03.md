## Why CrewAI Memory Is NOT Needed for This Bug

### The Problem

When user submits the question form with preferences, the message is:
```
"Here are my travel preferences: duration: 3-5 days, budget: mid-range, interests: nature"
```

The destination "Brazil" is in the **conversation history**, not the current message.

### Why CrewAI Memory Won't Help

1. **CrewAI hasn't run yet** - The crew only starts AFTER we have both destination + details
2. **Different memory scope** - CrewAI memory is for agent-to-agent context within/across crew executions
3. **Our history is external** - The destination lives in FastAPI's `history` parameter, not CrewAI's memory system

### The Simple Fix

Search the `history` list (which we already receive from FastAPI) for the destination:

```python
def _find_destination_in_history(self, history: list[dict]) -> str | None:
    """Search conversation history for a destination."""
    for msg in reversed(history[-6:]):
        if msg.get("role") == "user":
            destination = self._extract_destination(msg.get("content", ""))
            if destination:
                return destination
    return None
```

This is a 10-line fix vs. adding ChromaDB/SQLite infrastructure for CrewAI memory.

## When TO Use CrewAI Memory

### Memory Types Overview

| Type | Storage | Purpose | Use When |
|------|---------|---------|----------|
| **Short-Term** | ChromaDB (RAG) | Current execution context | Agents need to recall recent task outputs within a single run |
| **Long-Term** | SQLite3 | Persist insights across sessions | Building agent expertise over time (e.g., learning user preferences) |
| **Entity** | ChromaDB (RAG) | Track people, places, concepts | Complex domain with many entities to remember |
| **Contextual** | All combined | Holistic context | Need seamless integration of all memory types |

### Enable Memory

```python
from crewai import Crew

crew = Crew(
    agents=[...],
    tasks=[...],
    memory=True,  # Enables all memory types
    verbose=True
)
```

### Good Use Cases for CrewAI Memory

| Scenario | Memory Type | Why |
|----------|-------------|-----|
| Multi-turn trip refinement (same session) | Short-Term | Agent recalls earlier preferences without re-asking |
| Learning user's travel style over months | Long-Term | "User prefers budget accommodations, adventure activities" |
| Tracking places user has visited | Entity | Avoid recommending places they've already been |
| Complex research across many sources | Short-Term | Later agents reference earlier agent findings |
| Customer support with case history | Long-Term | Remember past interactions across sessions |

### When NOT to Use CrewAI Memory

- **Simple lookup from chat history** - Use Python to search the `history` list
- **One-shot tasks** - No value in persisting memory
- **Prototyping** - Adds complexity (ChromaDB, embeddings, storage)
- **Stateless APIs** - Memory requires persistence between requests

## LLM-Powered Intake: Dynamic Question Generation

### The Problem with Static Questions

The initial fix (`_find_destination_in_history()`) was fragile because:

1. **Regex-based detection** - Brittle pattern matching instead of semantic understanding
2. **Static questions** - Same 3 questions asked regardless of what user already told us
3. **Generic options** - "Nature & Landscapes" instead of "Amazon Rainforest" for Brazil

### Implementation Details

#### 1. TravelContext Pydantic Model

```python
class TravelContext(BaseModel):
    destination: str | None = None
    duration: str | None = None
    budget: str | None = None
    interests: list[str] | None = None
    travel_dates: str | None = None
    group_size: str | None = None
    special_requirements: str | None = None

    def get_missing_required(self) -> list[str]:
        """Return list of required fields that are still None."""
        required = ["destination", "duration", "budget"]
        return [f for f in required if getattr(self, f) is None]
```

#### 2. LLM-Powered Context Extraction

Instead of regex, we use Gemini with JSON mode:

```python
async def _extract_context(self, message: str, history: list[dict]) -> TravelContext:
    prompt = f"""Extract travel planning information from this conversation.
    Return JSON matching this schema: {TravelContext.model_json_schema()}
    Only include fields that are EXPLICITLY mentioned.
    """

    response = await self._call_gemini_json(prompt)
    return TravelContext.model_validate(response)
```

#### 3. Dynamic Question Generation

Questions are generated only for missing fields with destination-specific options:

```python
async def _generate_questions(self, context: TravelContext, missing: list[str]) -> list[dict]:
    prompt = f"""Generate intake questions for trip planning to {context.destination}.
    Generate questions ONLY for these missing fields: {missing}
    Make options SPECIFIC to {context.destination}.
    """

    return await self._call_gemini_json(prompt)
```

## Agent Context Persistence with Zustand Store

### Problem

Even with LLM-powered extraction, the travel agent was still losing context (destination, duration, etc.) after the questionnaire was submitted. The LLM-powered extraction from chat history wasn't reliable enough, and the questionnaire context wasn't being passed back to the backend.

### Solution: Frontend Zustand Store + SSE Updates

Instead of relying solely on LLM extraction from chat history, we implemented a Zustand store that:
1. Captures context from questionnaire events (via SSE)
2. Persists context per agent in localStorage
3. Sends the full context with each API request

### Architecture

```
Frontend Store (per agent)          Backend
┌─────────────────────┐            ┌─────────────────────┐
│ travelStore: {      │   SSE      │                     │
│   destination,      │ ◄───────── │ questionnaire event │
│   duration,         │            │ updates store       │
│   budget,           │            │                     │
│   interests         │   POST     │                     │
│ }                   │ ─────────► │ receives full       │
│                     │ +context   │ context each time   │
└─────────────────────┘            └─────────────────────┘
```

### Data Flow

1. **User sends message** → Frontend includes current agent context in request
2. **Backend processes** → Agent uses provided context (if available) or extracts via LLM
3. **Backend sends questionnaire** → SSE event with `context` field containing current state
4. **User submits form** → Answers merged with existing context, stored in Zustand
5. **Next message** → Full merged context sent with request

### Implementation Details

#### Frontend Store (`frontend/stores/agentContext.ts`)

```typescript

export type AgentContext = TravelContext; // Extensible for other agents

export const useAgentContextStore = create<AgentContextState>()(

      contexts: {},
      getContext: (agent: AgentType) => get().contexts[agent],
      updateContext: (agent: AgentType, context: Partial<AgentContext>) => {
        set((state) => ({
          contexts: {
            ...state.contexts,
            [agent]: { ...existing, ...context },
          },
        }));
      },
      clearContext: (agent: AgentType) => { ... },
      clearAllContexts: () => set({ contexts: {} }),
    }),
    { name: "agent-context-storage" }
  )
);
```

## Markdown Rendering in Chat Bubbles

### Problem

The travel agent outputs markdown-formatted responses with headers like:
```
## Destination Highlights
## Sample Itinerary
## Budget Estimate
```

These were rendering as raw `##` text instead of styled headers.

### Solution

Refactored `renderContent()` in `MessageBubble.tsx` to process content line by line and handle block-level formatting:

#### Before (inline-only rendering)
```typescript
function renderContent(content: string): React.ReactNode {
  // Only handled inline: citations, bold, code
  const regex = /(\[[^\]]+\])|(\*\*[^*]+\*\*)|(`[^`]+`)/g;
  // ... single-pass regex replacement
}
```

#### After (block + inline rendering)
```typescript
function renderInlineFormatting(text: string, keyPrefix: string): React.ReactNode {
  // Handle citations, bold, code within a line
}

function renderContent(content: string): React.ReactNode {
  const lines = content.split("\n");
  const elements: React.ReactNode[] = [];

  for (let i = 0; i < lines.length; i++) {
    const line = lines[i];

    // Headers: # ## ###
    const headerMatch = line.match(/^(#{1,3})\s+(.+)$/);
    if (headerMatch) {
      const level = headerMatch[1].length;
      const headerClasses = {
        1: "text-xl font-bold text-gray-900 mt-4 mb-2",
        2: "text-lg font-semibold text-gray-800 mt-3 mb-2",
        3: "text-base font-semibold text-gray-700 mt-2 mb-1",
      }[level];
      elements.push(<div className={headerClasses}>{renderInlineFormatting(headerText)}</div>);
      continue;
    }

    // Bullet points: - or *
    const bulletMatch = line.match(/^(\s*)[-*]\s+(.+)$/);
    if (bulletMatch) {
      elements.push(
        <div className="flex items-start gap-2">
          <span className="text-gray-400">•</span>
          <span>{renderInlineFormatting(bulletText)}</span>
        </div>
      );
      continue;
    }

    // Regular line or empty line
    if (line.trim() === "") {
      elements.push(<div className="h-2" />);
    } else {
      elements.push(<div>{renderInlineFormatting(line)}</div>);
    }
  }

  return elements;
}
```

### Supported Formatting

| Markdown | Rendered As |
|----------|-------------|
| `# Header` | Large bold header (text-xl) |
| `## Header` | Section header (text-lg) |
| `### Header` | Subsection header (text-base) |
| `- item` or `* item` | Bullet point with • |
| `**bold**` | Bold text |
| `` `code` `` | Inline code with background |
| `[file:10]` | Blue citation link |

## Chat State Migration to Zustand

### Problem

The frontend had state management spread across multiple locations:
- **Agent context** (destination, budget, etc.) → Zustand with localStorage persistence ✅
- **Messages, currentAgent** → useState in `useChat` hook (lost on refresh) ❌
- **Ephemeral UI state** (isLoading, error) → useState (fine) ✅

Users would lose their entire chat history on page refresh, and the "current agent" context would reset.

### Solution: New `chatStore.ts`

Created a second Zustand store specifically for chat state:

```typescript
// frontend/stores/chatStore.ts
interface ChatState {
  messages: Message[];
  currentAgent: AgentType;
  addMessage: (message: Message) => void;
  updateLastMessage: (updates: Partial<Message>) => void;
  setCurrentAgent: (agent: AgentType) => void;
  clearChat: () => void;
}

export const useChatStore = create<ChatState>()(
  persist(
    (set) => ({
      messages: [],
      currentAgent: "default",
      addMessage: (message) => set((state) => ({
        messages: [...state.messages, message],
      })),
      updateLastMessage: (updates) => set((state) => ({
        messages: state.messages.map((msg, i) =>
          i === state.messages.length - 1 ? { ...msg, ...updates } : msg
        ),
      })),
      setCurrentAgent: (agent) => set({ currentAgent: agent }),
      clearChat: () => set({ messages: [], currentAgent: "default" }),
    }),
    { name: "chat-storage" }
  )
);
```

### State Management Architecture

| State | Location | Persistence | Reason |
|-------|----------|-------------|--------|
| `messages` | Zustand `chatStore` | ✅ localStorage | Survive refresh, enable future features |
| `currentAgent` | Zustand `chatStore` | ✅ localStorage | Should persist with messages |
| Agent context (travel) | Zustand `agentContext` | ✅ localStorage | Per-agent structured data |
| `isLoading` | useState in useChat | ❌ None | Request-lifecycle bound |
| `error` | useState in useChat | ❌ None | Transient, should clear on refresh |
| `currentStatus` | useState in useChat | ❌ None | Streaming status, ephemeral |
| Slash menu state | useState in hook | ❌ None | UI-only, local to component |
| Form wizard state | useState in component | ❌ None | Temporary until submitted |

### Files Changed

- `frontend/stores/chatStore.ts` (NEW) - Zustand store for messages and currentAgent
- `frontend/hooks/useChat.ts` - Refactored to use chatStore instead of useState

### Data Flow

```
User types message
    ↓
useChat.sendMessage()
    ↓
chatStore.addMessage(userMessage)
chatStore.addMessage(assistantPlaceholder)
    ↓
SSE stream tokens arrive
    ↓
chatStore.updateLastMessage({ content: fullContent })
    ↓
Stream complete
    ↓
chatStore.updateLastMessage({ isStreaming: false })
    ↓
localStorage automatically synced by Zustand persist middleware
```

### Benefits

1. **Persistence** - Chat history survives page refresh
2. **Consistency** - All persistent state in Zustand stores
3. **Clean separation** - Ephemeral UI state stays local to hooks
4. **Future features** - Enables undo/redo, export, search, message editing
5. **DevTools** - Zustand state is inspectable in React DevTools

## Testing with Zustand Stores

### Problem: State Leakage Between Tests

After migrating chat state from `useState` in the `useChat` hook to a Zustand store (`chatStore`), tests started failing due to state persisting between test cases.

**Symptoms:**
```
✗ should handle agent events
  Expected messages length: 2
  Received messages length: 4  ← State from previous test leaked

✗ should clear all messages
  Expected messages length: 2
  Received messages length: 26  ← Accumulated from all prior tests
```

**Root Cause:**

Zustand stores are singletons that persist across test cases. Unlike React's `useState` (which resets per component mount), Zustand state survives until explicitly cleared.

```typescript
// This store instance is shared across ALL tests
export const useChatStore = create<ChatState>()(
  persist(
    (set) => ({
      messages: [],  // ← Accumulates across tests
      currentAgent: "default",
      // ...
    }),
    { name: "chat-storage" }
  )
);
```

### Solution: Reset Store in `beforeEach`

Add a `beforeEach` hook that clears the Zustand store before each test:

```typescript
// frontend/__tests__/useChat.test.ts
import { useChatStore } from "@/stores/chatStore";

describe("useChat", () => {
  beforeEach(() => {
    vi.clearAllMocks();
    // Reset Zustand store state before each test
    useChatStore.getState().clearChat();
  });

  // Tests now start with clean state...
});
```

### Why This Works

Zustand provides `getState()` to access store state outside of React components. This allows tests to:

1. Call store methods directly without rendering hooks
2. Reset state synchronously before each test
3. Ensure test isolation without mocking the entire store

### Alternative Approaches Considered

| Approach | Pros | Cons |
|----------|------|------|
| **Mock entire store** | Full isolation | Complex setup, doesn't test real store |
| **Reset in `afterEach`** | Works | Less reliable (cleanup might not run on failure) |
| **`beforeEach` with `getState()`** ✓ | Simple, reliable | Requires store to expose reset method |
| **Create new store per test** | Perfect isolation | Requires refactoring store creation |

### Best Practices for Zustand Testing

1. **Always provide a `clearXxx()` method** in stores that tests can call:
   ```typescript
   clearChat: () => set({ messages: [], currentAgent: "default" }),
   ```

2. **Reset in `beforeEach`, not `afterEach`** - ensures clean state even if previous test failed

3. **Import store directly in tests** - don't rely on hooks for reset:
   ```typescript
   import { useChatStore } from "@/stores/chatStore";
   // NOT: const { clearChat } = useChat();
   ```

4. **Consider disabling persistence in tests** - localStorage can also leak between tests:
   ```typescript
   // In test setup, you could mock the persist middleware
   vi.mock('zustand/middleware', () => ({
     persist: (fn) => fn,  // No-op persistence
   }));
   ```
