## Why CrewAI Memory Is NOT Needed for This Bug

### The Problem

When user submits the question form with preferences, the message is:
```
"Here are my travel preferences: duration: 3-5 days, budget: mid-range, interests: nature"
```

The destination "Brazil" is in the **conversation history**, not the current message.

### Why CrewAI Memory Won't Help

1. **CrewAI hasn't run yet** - The crew only starts AFTER we have both destination + details
2. **Different memory scope** - CrewAI memory is for agent-to-agent context within/across crew executions
3. **Our history is external** - The destination lives in FastAPI's `history` parameter, not CrewAI's memory system

### The Simple Fix

Search the `history` list (which we already receive from FastAPI) for the destination:

```python
def _find_destination_in_history(self, history: list[dict]) -> str | None:
    """Search conversation history for a destination."""
    for msg in reversed(history[-6:]):
        if msg.get("role") == "user":
            destination = self._extract_destination(msg.get("content", ""))
            if destination:
                return destination
    return None
```

This is a 10-line fix vs. adding ChromaDB/SQLite infrastructure for CrewAI memory.

## When TO Use CrewAI Memory

### Memory Types Overview

| Type | Storage | Purpose | Use When |
|------|---------|---------|----------|
| **Short-Term** | ChromaDB (RAG) | Current execution context | Agents need to recall recent task outputs within a single run |
| **Long-Term** | SQLite3 | Persist insights across sessions | Building agent expertise over time (e.g., learning user preferences) |
| **Entity** | ChromaDB (RAG) | Track people, places, concepts | Complex domain with many entities to remember |
| **Contextual** | All combined | Holistic context | Need seamless integration of all memory types |

### Enable Memory

```python
from crewai import Crew

crew = Crew(
    agents=[...],
    tasks=[...],
    memory=True,  # Enables all memory types
    verbose=True
)
```

### Good Use Cases for CrewAI Memory

| Scenario | Memory Type | Why |
|----------|-------------|-----|
| Multi-turn trip refinement (same session) | Short-Term | Agent recalls earlier preferences without re-asking |
| Learning user's travel style over months | Long-Term | "User prefers budget accommodations, adventure activities" |
| Tracking places user has visited | Entity | Avoid recommending places they've already been |
| Complex research across many sources | Short-Term | Later agents reference earlier agent findings |
| Customer support with case history | Long-Term | Remember past interactions across sessions |

### When NOT to Use CrewAI Memory

- **Simple lookup from chat history** - Use Python to search the `history` list
- **One-shot tasks** - No value in persisting memory
- **Prototyping** - Adds complexity (ChromaDB, embeddings, storage)
- **Stateless APIs** - Memory requires persistence between requests

For future agents needing production-grade memory storage:

### Quick Comparison

| Database | Type | Best For | Scale Limit | Pricing |

## LLM-Powered Intake: Dynamic Question Generation

### The Problem with Static Questions

The initial fix (`_find_destination_in_history()`) was fragile because:

1. **Regex-based detection** - Brittle pattern matching instead of semantic understanding
2. **Static questions** - Same 3 questions asked regardless of what user already told us
3. **Generic options** - "Nature & Landscapes" instead of "Amazon Rainforest" for Brazil

### New Architecture: LLM-Powered Intake

### Implementation Details

#### 1. TravelContext Pydantic Model

```python
class TravelContext(BaseModel):
    destination: str | None = None
    duration: str | None = None
    budget: str | None = None
    interests: list[str] | None = None
    travel_dates: str | None = None
    group_size: str | None = None
    special_requirements: str | None = None

    def get_missing_required(self) -> list[str]:
        """Return list of required fields that are still None."""
        required = ["destination", "duration", "budget"]
        return [f for f in required if getattr(self, f) is None]
```

#### 2. LLM-Powered Context Extraction

Instead of regex, we use Gemini with JSON mode:

```python
async def _extract_context(self, message: str, history: list[dict]) -> TravelContext:
    prompt = f"""Extract travel planning information from this conversation.
    Return JSON matching this schema: {TravelContext.model_json_schema()}
    Only include fields that are EXPLICITLY mentioned.
    """

    response = await self._call_gemini_json(prompt)
    return TravelContext.model_validate(response)
```

#### 3. Dynamic Question Generation

Questions are generated only for missing fields with destination-specific options:

```python
async def _generate_questions(self, context: TravelContext, missing: list[str]) -> list[dict]:
    prompt = f"""Generate intake questions for trip planning to {context.destination}.
    Generate questions ONLY for these missing fields: {missing}
    Make options SPECIFIC to {context.destination}.
    """

    return await self._call_gemini_json(prompt)
```

### SSE Event Flow

```
1. User: "/travel Brazil for 5 days"
2. Backend: status("Analyzing your request...")
3. Backend: _extract_context() → {destination: "Brazil", duration: "5 days"}
4. Backend: get_missing_required() → ["budget", "interests"]
5. Backend: status("Preparing questions...")
6. Backend: _generate_questions() → contextual questions for Brazil
7. Backend: questionnaire({title: "Planning trip to Brazil", steps: [...]})
8. Frontend: Renders multi-step wizard
9. User: Selects budget, interests
10. Frontend: Submits answers as new message
11. Backend: _extract_context() → all fields now filled
12. Backend: status("Planning your trip...")
13. Backend: CrewAI agents execute
```
